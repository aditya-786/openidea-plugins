# Spring Endpoints Tools

One **Spring Endpoints** tool window (right) with six sections, plus the editor support of six former plugins: Spring Web (this one), Spring WebSocket, Spring Messaging, Spring for GraphQL, Spring Web Flow and Spring Cloud.
MIT; see `LICENSE`.

`aritti.spring-websocket`, `aritti.spring-messaging`, `aritti.spring-graphql`, `aritti.spring-webflow` and `aritti.spring-cloud` are no longer maintained: uninstall them, otherwise their windows and completions show twice. Settings keep their keys (`springWeb.*`, `springWebsocket.*`, `springGraphql.*`, `springCloud.*`); the old plugins' values are not migrated.

## Spring Endpoints window

- **HTTP**: the route list of the Spring Web section below, with its controller filter, Flat/Tree toggle and row actions.
- **WebSocket**, **Messaging**, **GraphQL**: the STOMP destinations, the Kafka/RabbitMQ/JMS destinations and the GraphQL endpoints and schema files.
- **Web Flow**: the diagram of the flow in the active editor.
- **Feign**: the project's Feign client methods per file.

A module whose dependency is not in the root build file (multi-module builds and version catalogs count as unsure) does no work.

The registered `window::Endpoints` wrapper owns API 1.3 current-document diagnostics. It returns one merged response for the active HTTP, WebSocket, messaging, GraphQL, Web Flow and Cloud modules; embedded marker providers no longer publish or recompute these checks. Diagnostics and hover read current unsaved text and cached facts only. Dependency applicability and module indexes warm during activation/file events, outside editor requests. Optional event denial, cold/stale/incomplete reads, failed reads and oversized project inputs suppress absence-based findings. Current input is limited to 128 KiB and the merged response to 500 findings.

## Spring Web

Spring MVC helpers for Java controllers (Kotlin controllers included, see below):

- **Endpoints list** (HTTP section): a flat list: the generic native endpoint icon, the path, and grey text with `[METHOD] Controller` after it. *Filter* narrows the list to one controller (the status line says which), *Clear* restores it, and *Flat/Tree* groups the rows by controller. Row actions: *Copy as curl* and *Create HTTP Request File* (writes `http/<verb>-<path>.http`, needs `process:tee`; without it the request is copied). Limits: the grey text follows the path rather than sitting in a column, there is no request panel beside the list, and no gutter icon on the handler; these wait on upstream OpenIDEA requests.
- **Path variables**: in `@Controller`/`@RestController` handler methods, a `@PathVariable` whose name (`value`/`name`, else the parameter name) is missing from one of the method's mapped paths (class `@RequestMapping` prefix included) is an error; when exactly one template variable is left unbound, a quick fix renames the parameter's variable to it. A `{variable}` of a method mapping that no `@PathVariable` takes is a warning, unless a `@PathVariable Map` or a form object (`@ModelAttribute`, or an unannotated parameter of a non-framework type) may bind it. The `{name}`, `{name:regex}` and `{*name}` forms are supported.
- **API versions**: a request mapping that sets `version` (Spring Framework 7) is a warning when the project configures no API versioning. Quiet unless every source and `application*` file was read, at least one `application*` file exists, and none mentions `apiversion` (`spring.mvc.apiversion.*`) or `ApiVersion…`/`configureApiVersioning`. Setting `springWeb.checkApiVersioning`. In tests, a Hint on `apiVersion(...)` when the project mentions neither `ApiVersionInserter` nor `spring.mvc.apiversion.*` in any file.
- **@InitBinder**: an `@InitBinder` method that returns a value (error, Spring throws) or takes no `WebDataBinder`/`DataBinder` parameter (warning). Setting `springWeb.checkInitBinder`.
- **View names**: in `@Controller` handler methods without `@ResponseBody`, `return "users/list";`, `new ModelAndView("…")` and `setViewName("…")` get a gutter arrow and Go to Definition to the template, and completion of template names. Templates are looked up in `src/main/resources/templates/` (`.html`, `.ftlh`, `.ftl`, `.mustache`, `.peb`, `.jte`, `.kte`), `src/main/webapp/WEB-INF/{views,jsp}/` (`.jsp`) and where `spring.mvc.view.prefix/suffix` or `spring.thymeleaf.prefix/suffix` point. `redirect:` and `forward:` views are skipped, and a Thymeleaf `name :: fragment` resolves to `name`. An unknown view name is not reported, since another view resolver may handle it. XML `<mvc:view-controller view-name>` and Java `addViewController(...).setViewName(...)` navigate to their templates too.
- **Unresolved views** (`springWeb.reportUnresolvedViews`, default on): a Hint on a returned view name that no template of the known folders answers, once the project has at least one template. Quiet until every source was read, and for good when any source mentions `ViewResolver`, `ViewResolverRegistry`, `configureViewResolvers`, `TilesConfigurer` or `AbstractView`, since another resolver may serve the name. (The unresolved-template inventory needed for a stronger check is not modeled.)
- **Functional routes**: `RouterFunctions.route().GET("/x", handler)` (also `POST`/`PUT`/`DELETE`/`PATCH`/`HEAD`/`OPTIONS`), `route(RequestPredicates.GET("/x"), handler)`, `.andRoute(…)`, and the prefixes of `.path("/api", b -> …)` and `.nest(path("/api"), b -> …)` are read as endpoints, as are the Kotlin `router {}`/`coRouter {}` DSL (`GET("/x")`, `"/api".nest { … }`, `nest(path("/api")) { … }`). A handler written `this::list`, `Handler::list` or Kotlin `::list` gets a gutter arrow and Go to Definition to the project method. Kotlin sources are indexed for routes, controller checks and literal view navigation (`**/*.kt`). A route under a `nest` whose predicate is not a plain `path("…")` (including Kotlin `("/a" and accept(…)).nest { }`) is skipped. Kotlin `"/a".nest { }`, `"/a" nest { }` and `path("/a").nest { }` are read.
- **Test URLs**: in `src/test/` sources, a URL literal of `mockMvc.perform(get("/users/{id}", 1))` (any HTTP method, also `MockMvcRequestBuilders.get`), `webTestClient.get().uri("/users")` (also `WebClient`/`RestClient`) and `restTemplate.getForObject("/users", …)`/`exchange("/users", HttpMethod.GET, …)` gets a gutter arrow and Go to Definition to the request mappings that serve it, matched by HTTP method and URI template (`{id}` matches any segment; `*`, `**`, `{*rest}` and mixed segments like `by-{name}` work). Every matching mapping is offered; `{id:regex}` constraints are ignored when matching, so more mappings than Spring would pick may be offered; absolute URLs (`http://…`) are skipped; a URL no mapping serves is left alone. The RestTemplate calls need a receiver named like `restTemplate`/`template`. Mappings are those with literal paths in `@Controller`/`@RestController` classes and functional routes.
- **URL markers**: every request mapping and functional route shows its URL (`URL: GET /users/{id}`) in the gutter, unless a link marker already uses the line. Setting `springWeb.showUrlMarkers`. The marker has no target.
- **URL completion in tests**: inside the URL literal of `mockMvc.perform(get("…"))`, `webTestClient.get().uri("…")` and `restTemplate.getForObject("…")`, the project's mapping paths for that HTTP method are offered.
- **Static resources**: Go to Definition on a string literal such as `"/css/app.css"` or `"classpath:/static/js/a.js"` opens the file under a `static/`, `public/` or `META-INF/resources/` folder of the project (`css`, `js`, images, fonts, `html`). Literal HTML/JSP `src`/`href` and Thymeleaf `@{/asset}` links navigate to Spring static roots, including query/fragment suffixes; dynamic expressions and commented markup are skipped.
- **Snippets** (Java and Kotlin, with tab stops): in a controller class body `getm`, `postm`, `putm`, `delm`, `patm`, `reqm` (mapping methods), `exh` (exception handler) and `initb` (init binder); in any class body `router` (functional `RouterFunction` bean, Kotlin `router {}`); outside every type `restc`, `ctrl` and `advice` (controller classes). Snippets add no imports.
- **File templates**: New menu entries Spring Controller, REST Controller and Controller Advice, for Java and Kotlin (`$PACKAGE$`, `$NAME$` and `$END$`; the host drops the `package` line when there is no package).
- **Kotlin controllers**: the path variable, API version and `@InitBinder` checks run on Kotlin controllers, and the Add `@RequestMapping`/`@ExceptionHandler` method actions generate Kotlin (`fun handle(): String`, no semicolons in the import).
- **HTTP request files**: on an endpoint in the Endpoints view, Create HTTP Request File for Endpoint asks for the base URL and writes `http/<verb>-<path>.http` under the project root (`### GET /users` plus the request line) and opens it; an existing file is opened untouched. Needs the optional `process:tee` capability; without it the request goes to the clipboard (optional `clipboard`). Sending a request stays with the IDE's HTTP client. HTTP request files (`.http`/`.rest`) also complete literal Spring paths and navigate request paths to local handlers; absolute HTTP(S) and `{{host}}` authorities and query text stay outside replacement ranges, and request bodies are not scanned as requests. HEAD completion includes GET mappings. Native HTTP-file endpoint completion is owned by the host through `EndpointsProvider`; this plugin supplies path definition navigation and only supplements missing HEAD-to-GET completion, using native `{{name}}` variable syntax and excluding paths already supplied by explicit HEAD/ANY mappings.
- **`<mvc:…>` XML**: source-owned schema profiles cover 54 element rows across official 3.0–4.3, 5.3, 6.2 and current namespaces, with required attributes, boolean/integer values and local unique bean references. MVC XML bean refs resolve through local `<import>` closures and `<beans profile>` blocks (Info for profile-only and undeclared beans); `<mvc:resources>` locations are checked under `src/main/resources` and `src/main/webapp`. Unknown namespace versions and unsupported contracts remain unclaimed.
- **Thymeleaf fragments and models**: literal Thymeleaf fragment expressions (`th:insert`, `th:replace`, legacy `th:include` and HTML5 data attributes) offer known template/fragment completion and definition navigation; named fragments resolve to exact `th:fragment` declarations, same-template fragments use unsaved source, and `th:replace '~{layout :: #id}'` selectors jump to the unique element with that id. Dynamic selectors, parameterized invocations and runtime template-stack resolution are not inferred. Source-declared MVC model names complete/navigate in matching Thymeleaf templates: literal `Model`/`ModelMap.addAttribute` values and explicitly named `@ModelAttribute` methods are tied to the handler's returned view; local `th:each`/`th:with` names are excluded. This is positive name navigation, without member typing or claims that unknown/runtime attributes are missing.
- **SpEL injection**: the optional **Enable Thymeleaf SpringEL support** injects exact `${...}`/`*{...}` attribute ranges into the `spel` language supplied by the Spring Beans plugin. It defaults off because standalone Spring Web does not provide that language. Entity-escaped or composite expression mappings are withheld; no embedded semantic LSP or rendered expression colorization is claimed. Spring MVC `#{...}` SpEL in `@RequestParam`, `@RequestHeader` and `@CookieValue` `defaultValue` is injected as `spel` behind this opt-in (JSP EL injection is not implemented).

Matching is text-based. Mapping paths written as constants, concatenations or `${…}` placeholders are not checked. Not implemented: HTTP client execution (built into OpenIDEA), URL completion in other HTTP clients beyond these request files and test calls, typed template-model members and JSP EL model resolution, a versioned template inventory for a stronger unresolved-view check.

## Spring WebSocket

STOMP messaging support for Spring Java and Kotlin projects:

- **Index** of the project's broker configuration (`enableSimpleBroker`, `enableStompBrokerRelay`, `setApplicationDestinationPrefixes`, `setUserDestinationPrefix`, `addEndpoint` in a `WebSocketMessageBrokerConfigurer`), handlers (`@MessageMapping`, `@SubscribeMapping`, class-level `@MessageMapping` prefix joined) and destinations sent to (`@SendTo`, `@SendToUser`, `convertAndSend`, `convertAndSendToUser`, `send` of a messaging template).
- **Gutter arrows**: a handler shows the destination a client uses (`SEND /app/chat/send`). A destination sent to links to the other places that use it, and Go to Definition on the literal lists them all. User destinations match as the client sees them (`/user/queue/replies`).
- **Completion** in destination literals: broker prefixes and known destinations.
- **Warning** on a broker destination that no configured broker prefix covers. It only appears when the project configures a broker, and never on user destinations.
- **Broker-prefix/XML checks** run through the merged current-document diagnostics described above.

Matching is text-based, on destination literals as written; `${…}` placeholders and destinations built from variables are skipped. A `convertAndSend`/`send` call counts when its receiver is named like a messaging template (`messagingTemplate`, `simp…`), or when the destination starts with `/` and the receiver isn't a Kafka, Rabbit or JMS template.

- **JavaScript/TypeScript STOMP clients** (`.js`, `.jsx`, `.ts`, `.tsx`, `.vue`, outside `node_modules`, `dist`, `build`): `client.subscribe('/topic/x', …)` links to the matching `@SendTo`/`convertAndSend`/`@SubscribeMapping`, and `client.publish({ destination: '/app/x' })` or `client.send('/app/x', …)` links to the `@MessageMapping` handler (application prefix applied). The Java side lists the client usages in its gutter tooltip. A call counts when its receiver name contains `stomp`, or was assigned `new Client(`, `new StompJs.Client(`, `Stomp.over(` or `Stomp.client(` in the same file (`httpClient.send` and the like are ignored). Only plain string literals starting with `/` count; template strings with `${…}` and concatenations are skipped. One target opens per marker; the tooltip lists the rest.

  JS/TS/Vue documents are only read and linked in a project whose root `pom.xml`, `build.gradle` or `build.gradle.kts` mentions `spring-boot-starter-websocket`, `spring-messaging` or `spring-websocket`, or once a Java or Kotlin file of the project has been opened in the session; elsewhere they are left alone (no scan of the project). A backend in a sub-module with no such root build file is picked up only after one of its Java/Kotlin files is opened.

- **Spring XML** (`http://www.springframework.org/schema/websocket`): required attributes of `stomp-endpoint` (`path`), `mapping` (`path`, `handler`), `simple-broker` and `stomp-broker-relay` (`prefix`) and `handshake-handler` (`ref`); a `handler`/`ref` that names no bean of the project is an Info (beans of libraries are invisible; quiet until the whole project was read). The tables are hard-coded since no schema is at hand.

Not implemented: raw `WebSocketHandler` registration checks, SockJS options.

## Spring Messaging

Producer ↔ consumer navigation for Spring Kafka, Spring AMQP (RabbitMQ) and Spring JMS (ActiveMQ/Artemis) in Java and Kotlin projects:

- **Index** of every destination literal:
  - consumers: `@KafkaListener(topics = …)`, `@RabbitListener(queues = …)` (plus `queuesToDeclare = @Queue(…)` and `bindings = @QueueBinding(value = @Queue(…), exchange = @Exchange(…))`, which consume the queue and the exchange), `@JmsListener(destination = …)`;
  - producers: `send` of a Kafka template, `new ProducerRecord<>("topic", …)`, `convertAndSend`/`send`/`convertSendAndReceive` of a Rabbit template (`(routingKey, msg)` goes to the queue of that name through the default exchange, `(exchange, routingKey, msg)` to the exchange), `convertAndSend`/`send` of a JMS template, `@SendTo` on a listener method (`exchange/routingKey` for Rabbit);
  - declarations: `TopicBuilder.name`, `new NewTopic`, `new Queue`, `QueueBuilder.durable/nonDurable`, `new TopicExchange`/`DirectExchange`/`FanoutExchange`/`HeadersExchange`, `ExchangeBuilder.*Exchange`, `new ActiveMQQueue`/`ActiveMQTopic`.
- **Gutter arrows**: a consumer links to the producers and declarations of its destination, a producer to its consumers. Go to Definition on a destination literal lists every other place naming it. A literal `RabbitTemplate` `convertAndSend`/`send` call also links to the exchange's `BindingBuilder` routing key (Info for an unbound key on a complete index).
- **Completion** of known destination names (same broker, same kind: topic, queue, exchange or JMS destination) inside those literals.
- **Messaging** section of the Endpoints window: broker → destination → consumers, producers and declarations; a click opens the place, Refresh rescans.

Matching is text-based, by exact name. The broker of a `send`/`convertAndSend` comes from the receiver's name (`kafkaTemplate`, `rabbitTemplate`, `jmsTemplate`…) or, failing that, the declared type of the field or parameter it names; calls on anything else (`streamBridge`, a messaging template) are left out. SpEL is skipped. Destinations written as a `static final String` (Java) or `const val` (Kotlin) constant, `Queues.ORDERS`, are read through the string constants of the project (literals and `+` chains in one file; a bare `NAME` only inside its own class); a constant the project does not define is dropped. There are no warnings for destinations, because a destination may be produced or consumed outside the project.

Placeholders: `${key}` and `${key:default}` in `topics`, `queues`, `destination`, `@SendTo` and in send calls are resolved from `application*`/`bootstrap*` `.properties`, `.yml` and `.yaml` files of the project (keys match relaxed: `app.topic-name` = `app.topicName`), a default or a value holding another placeholder down to two levels, and only for unambiguous property keys. `application.*` wins over profile files (`application-dev.*`), then the rest in path order; the active profile is unknown to plugins, so a value that differs per profile takes the first file's. A placeholder that can't be resolved, or that resolves to a comma-separated list, gets no link. Rabbit `@SendTo("${…}")` is skipped (the `exchange/routingKey` form can't be told apart).

XML listeners: `<jms:listener destination>` and `<rabbit:listener queue-names>` (bean-name `queues` are not read) in Spring XML files link their destination like annotated consumers; `ref` and `method` go to the bean (XML `<bean>`, stereotypes, `@Bean` methods) and its class's methods, and complete.

XML checks (hand-written tables, not read from the XSDs; only these elements): Rabbit `listener` needs `ref`, `listener-container` `acknowledge` is `auto|manual|none`, the four exchange elements need `name`, `queue`/exchange booleans (`durable`, `exclusive`, `auto-delete`) are `true|false`; JMS `listener` needs `destination` and `ref`, `listener-container` `acknowledge`, `container-type`, `destination-type` and `cache` take their schema values. A `ref` naming no bean of the project is Info only (library and container beans are invisible); a `method` the project class does not have is a warning, quiet when the class extends or implements anything. Values with `${}`/`#{}` are skipped. Also: `true`/`false` values of Rabbit `connection-factory` (`publisher-confirms`, `publisher-returns`), `admin` (`auto-startup`, `ignore-declaration-exceptions`) and `listener-container` (`auto-declare`, `mismatched-queues-fatal`). Other namespace elements (`template`, `binding`, `annotation-driven`, `jca-listener-container`) are not modelled: their schemas were not at hand to list them completely.

Kotlin sources are indexed too (array literals, `suspend` and expression-bodied functions), except the nested `queuesToDeclare`/`bindings` annotations, which are read in Java only.

SpEL destinations: a whole-value template `"#{'orders'}"`, `"#{'a' + 'b'}"`, `"#{'${app.topic}'}"` (placeholders resolve as usual) and `"#{T(com.acme.Queues).ORDERS}"` (a constant of the project) is read as that name. Anything that needs evaluating (`@bean.method()`, conditions, a constant joined to a literal) is skipped.

Not implemented: broker connection and live topics, Spring Cloud Stream bindings (a separate plugin), SpEL beyond the destinations above, `BindingBuilder` routing beyond the Rabbit exchange link, constants held in non-constant expressions or other projects' classes.

## Spring for GraphQL

Links Spring for GraphQL controllers to their schema. The GraphQL language itself (highlighting, the optional language server) is built into the IDE.

- **Handler → schema**: a gutter arrow on each `@QueryMapping`, `@MutationMapping`, `@SubscriptionMapping`, `@SchemaMapping` and `@BatchMapping` method of a `@Controller` opens its schema field; Go to Definition works on the method name and the annotation.
- **Schema → handler**: in `.graphqls`/`.graphql` files, a gutter arrow on each field served by a controller method, and Go to Definition from the field name.
- **Kotlin controllers** (`.kt`) are read like the Java ones, `suspend fun` and expression bodies included.
- **Client documents**: Go to Definition on a field of a query, mutation or subscription in `.graphql`/`.gql` files under `graphql-documents/` and in `.document("…")` literals (text blocks too, Java and Kotlin) opens the schema field, and for a root field its controller method. Nested fields resolve through the declared field types. Fragments and spreads are only followed for `fragment X on Type`; inline fragments, and literals with escapes, are skipped. No problems are reported for unknown fields.
- **Completion** of type names in `typeName = "…"` and of field names in `field`/`name`/`value = "…"`.
- **Checks**: a warning on a handler whose `Type.field` the schema doesn't declare (only when the schema declares that type, or for a root type when the project has a schema), and on an `@Argument` whose name isn't one of the field's arguments; a hint on `Query`/`Mutation`/`Subscription` fields no controller method serves (they may come from `DataFetcher` beans or Querydsl/Query by Example repositories). Literal `RuntimeWiringConfigurer` data fetcher registrations count as GraphQL handlers and relax the unmapped-field gate only when every `RuntimeWiring` mention is a recognised registration (a proven `RuntimeWiring.Builder` receiver, configure parameter or lambda parameter). An Info hint is reported for unhandled argument fields on served object types when the handler set is provably complete.
- **Unmapped fields** (Info, setting `springGraphql.reportUnmappedFields`): in a schema file, a field with arguments on an object type that no controller method serves (`@SchemaMapping`, `@BatchMapping`) is reported, because the default property fetcher ignores arguments. Quiet when any source mentions `DataFetcher`, `RuntimeWiring`, `GraphQlSourceBuilderCustomizer` or `DataLoader`, and for root types.
- **GraphQL** section of the Endpoints window, with the HTTP path (`spring.graphql.path`, default `/graphql`), the WebSocket path, GraphiQL and the schema printer when enabled, prefixed with `server.servlet.context-path`, and the schema files. Rows from a configuration file open it at the key.

How matching works: every `*.graphqls`/`*.graphql` file outside `node_modules` is read as SDL (`type`, `interface`, `input`, `extend type` and the `schema { query: … }` block; operations are skipped; enums/scalars and union return shapes are recorded), files under `resources/graphql/` first. A shortcut handler's type is its fixed annotation parent (`Query`, `Mutation` or `Subscription`), even when SDL declares a different operation root. Other mapping parents use method `typeName`, else the class-level `@SchemaMapping(typeName)`, else the simple type of the source parameter (the first one that isn't an `@Argument`/`@ContextValue`/… or an environment type such as `DataFetchingEnvironment`), or the element type of a `@BatchMapping`'s `List<T>`. Its field is the annotation's `field`/`name`/`value`, else the method name. Text-based: types match by simple name, as written.

Not implemented: additional subscription protocols and transports beyond the optional `graphql-transport-ws` adapter described below (legacy protocol, SSE and RSocket); checks of client documents (unknown fields, arguments), completion inside them, and documents built from variables or concatenation; Federation directives (`@key`, `@external`…) are skipped, not understood.

## Spring Web Flow

Spring Web Flow 2 and 3 XML flow definitions (files whose root is `<flow>` in the `http://www.springframework.org/schema/webflow` namespace):

- **States**: Go to Definition and completion on `to` of `<transition>`, `then` and `else` of `<if>` in a `<decision-state>`, and `start-state` of `<flow>`. They lead to the state of the same flow, then to a state inherited from a parent flow.
- **Flows**: `subflow` of `<subflow-state>` and `parent` of `<flow>` (comma-separated) open the flow file and complete flow ids; `parent="flowId#stateId"` on a state opens the parent flow or its state, and completes that flow's states. A flow's id is its file name without `.xml`. A flow registry in the project's XML (`webflow-config` namespace) adds ids: `<flow-location id path>` names the file at that path, and `<flow-registry base-path>` names a flow in a subfolder after that folder (`/WEB-INF/flows/booking/booking-flow.xml` is `booking`).
- **Checks**: a transition, `then` or `else` naming no state of the flow or its parents is an error, so is a `start-state` naming no state and a state id used twice. A `subflow` naming no known flow is a warning, once the whole project has been read. A flow without an `<end-state>` gets a note, unless it is abstract or has a parent. Expressions (`${…}`, `#{…}`) are never reported, and state checks are skipped while a parent flow can't be found.
- **Web Flow** section of the Endpoints window: the flow of the active editor as a diagram. Each state shows its id and kind, the start state is highlighted, and transitions are arrows labelled with their `on` event. A decision's arrows show the `test` of each `<if>` (cut short, full text on hover) and `else`. It follows the focused editor and the edits to the flow; Refresh redraws it. Global transitions aren't drawn. The graph renders bounded well-formed flow XML with unique state ids (128 states/256 transitions); unresolved/global/self edges omitted by the layout remain outside drawn-edge coverage. State clicks open their current source declaration; drawn transition/decision edges open their current target attribute; forged/unknown ids, missing or changed project ownership and malformed/over-budget sources are refused. These are source links, not a runtime flow, inherited-state or reachability model.
- **Add reviewed local Web Flow transition…**: a lazy FileAction in an XML editor on a supported view-state. Choose a direct state in the same file, enter a new literal event, then review the exact source replacement. It returns one undoable text edit, expanding a self-closing state when needed; no direct source write, file create, process, network, build or database action occurs. Namespace prefixes, current unsaved text, UTF-16 ranges and CRLF are preserved. Ownership, full text, document version and project-visible source are checked around every prompt and the final exact confirmation. Inherited/abstract flows, global transitions, ambiguous ids, dynamic/wildcard or duplicate events, unknown state targets and complex state bodies remain quiet. The adapter only admits empty view-states or existing empty literal transitions, preserving the XSD's child ordering (transitions before `on-exit` and `exception-handler`) without moving unknown content. This is a conservative source-local creation subset, not all XSD/schema/runtime validation or support for action/subflow/decision/global transition editing.

Matching is text-based: ids as written in attributes. Flows registered in Java configuration (`FlowDefinitionRegistryBuilder`), in libraries or in other modules aren't seen. Not covered: view and bean references (`view`, `expression`, `evaluate`), flow input/output mappings and SpEL in expressions.

## Spring Cloud

Spring Cloud OpenFeign, Spring Cloud Stream and Spring Cloud Gateway support for Java and Kotlin projects and `application*`/`bootstrap*` `.properties|yml|yaml` files:

- **Feign client → endpoint**: a gutter arrow on each method of a `@FeignClient` interface whose request matches a `@RestController`/`@Controller` method of the project, and Go to Definition from the method name. A client's request is its `@GetMapping`/`@PostMapping`/`@PutMapping`/`@DeleteMapping`/`@PatchMapping`/`@RequestMapping` (a `@RequestMapping` without `method` counts as GET) or Feign's `@RequestLine("VERB /path")` (the query string is dropped), prefixed by the client's `path`.
- **Endpoint → Feign client**: a gutter arrow on each controller method called by a Feign client method. Spring `@HttpExchange`/`@GetExchange`/`@PostExchange`/`@PutExchange`/`@DeleteExchange`/`@PatchExchange` interfaces are listed as client endpoints with request drafts; Feign `contextId`/`configuration` are shown.
- **Feign check**: a warning on an abstract Feign client method with no request mapping, lowered to an info when the `@FeignClient` sets `configuration` (which may bring another contract).
- **Function bean → bindings**: a gutter arrow on each `Function`, `Consumer` or `Supplier` bean (a `@Bean` method returning one, or a `@Component`/`@Service`/… class implementing one) to the binding keys named after it (`process-in-0`, `process-out-0`) under `spring.cloud.stream.bindings.` and `spring.cloud.stream.function.bindings.`, then to its entries in `spring.cloud.function.definition`. A function that is part of a composed definition (`uppercase|process`) also links to the bindings of the composition (`uppercaseprocess-in-0`).
- **Binding → function bean**: Go to Definition on a binding name or on a `spring.cloud.function.definition` entry opens the bean (each part of a composed function).
- **Completion** of bean names in `spring.cloud.function.definition` (after `;` and `|`), of binding names after `spring.cloud.stream.bindings.` (`<bean>-in-0` for a `Consumer`, `<bean>-out-0` for a `Supplier`, both for a `Function` and for composed definitions), and of the predicates and filters shipped with Spring Cloud Gateway in a route's `predicates`/`filters` list items (inserted as `Name=`). Gateway factory completion includes project-defined predicate/filter factories in their own kind; expanded `.name` properties are completed without shortcut `=` separators and checked against the same kind.
- **Stream checks** (warnings): a `<name>-in-N`/`<name>-out-N` binding whose `<name>` is no function bean, definition entry, composed definition, `spring.cloud.stream.output-bindings`/`input-bindings`/`source` name, `spring.cloud.stream.function.bindings` alias or literal passed first to a `send(…)` call (`StreamBridge`); a `spring.cloud.function.definition` entry naming no function bean. These checks run once the project's Java and Kotlin files have been read, and only when the project declares at least one function bean (functions may come from libraries).
- **Unbound channels** (hint): `streamBridge.send("name", …)` with a literal name, or a binder-specific key (`spring.cloud.stream.kafka.bindings.<name>.…`), where no `spring.cloud.stream.bindings`, declared binding, alias or function of the project matches `<name>`. StreamBridge would create the binding on the fly with default settings, so this is most likely a typo. Quiet until the whole project is read, while the project has no explicit bindings, and for `${…}` names. Setting `springCloud.checkStreamBindings`.
- **Bootstrap file** (warning): a `bootstrap*.yml|yaml|properties` file while the build files (`pom.xml`, `build.gradle[.kts]`) state a Spring Boot version of 2.4 or later and none mentions `spring-cloud-starter-bootstrap`, `spring.cloud.bootstrap.enabled=true` or legacy config processing. Since Boot 2.4 such a file is ignored; use `spring.config.import` or add the starter. Quiet when the Boot version is not a literal, any module has the starter or a version below 2.4 is found. Setting `springCloud.checkBootstrap`.
- **Legacy Stream** (`springCloud.checkLegacyStream`): a literal channel of `@StreamListener` or `@SendTo` that no `@Input`/`@Output` method of the project declares (warning; quiet unless every `@EnableBinding` type is a project interface or `Sink`/`Source`/`Processor`, and the project is fully read); a `@StreamListener` method that returns a value without `@SendTo`/`@Output`, and `@SendTo` on a void method (info); a `@BootstrapConfiguration` class that is also `@Configuration`/`@Component` (hint: component scanning may load it twice).
- **Stream handler signatures** (`springCloud.checkLegacyStream`, warning): a `@StreamListener` method that names its input twice (on the annotation and on an `@Input` parameter) or not at all, that has both `@SendTo`/`@Output` on the method and an `@Output` parameter, that returns a value while taking an `@Output` parameter, or that sets `condition` with a `Flux`/`Mono`/`Publisher` parameter. Spring Cloud Stream rejects each of these at startup.
- **Feign** section of the Endpoints window: a tree of the project's Feign client methods per file; double-click opens the method. The Endpoints window also shows literal `@RequestMapping` names (class#method). Spring Cloud key value hints come from the Spring Boot Tools plugin's bundled metadata, so there is nothing to add here.
- **Gateway checks**: a route predicate or filter that Spring Cloud Gateway doesn't ship and no class of the project provides (a class named `…RoutePredicateFactory`/`…GatewayFilterFactory`, or extending a `…PredicateFactory`/`…FilterFactory`). It is a warning for `spring.cloud.gateway.routes` and `spring.cloud.gateway.server.webflux.routes`, and an info for the WebMVC lists `spring.cloud.gateway.server.webmvc.routes` and `spring.cloud.gateway.mvc.routes`. These checks run once the project's Java and Kotlin files have been read. Recognised predicates/filters include the shortcut form (`- Path=/users/**`); the Weight expanded keys are `weight.group`/`weight.weight` with group required, and the Retry shortcut limit is 9 (jitter and timeout on latest main are not modelled).

**Service-aware Feign navigation:** literal `@FeignClient(name = "users")`, `value = "users"` and shorthand `@FeignClient("users")` are compared with the destination module's source-declared `spring.application.name`. A known different service is excluded from both Go to Definition and forward/reverse gutter navigation, even if its controller has the same HTTP method and path. `contextId` is not used as a service name. Single targets remain direct links; multiple source targets on a line open a native chooser showing the method and relative source path. The chooser revalidates the project, source version, configuration and candidate locations before and after selection; Cancel opens nothing.

The first version supports conventional Maven/Gradle `src/main/java`, `src/main/kotlin` and `src/main/resources` layouts within one opened project, with base `application.properties`, `application.yml` or `application.yaml` directly in resources or its `config/` directory. Names are compared exactly. The configuration inventory must be complete, with one consistent literal name across the module's indexed application/bootstrap files. Conflicting or dynamic names, duplicate declarations, configuration imports, profile-only identities and multi-document configuration do not narrow candidates. Configuration is never inherited from a parent/sibling module or test resources. Missing/unsupported identities and clients with explicit or dynamic `url` retain method/path candidates; these are source candidates, not proof of the runtime destination. Active profiles, environment overrides, discovery registries, separate project roots and custom source sets are not resolved. No network request or process is started. The picker is bounded to 256 candidates per line and 32 pending actions; incomplete revalidation asks the user to retry.

Text-based, Java and Kotlin: a Feign method matches an endpoint by HTTP method and path segments (`{…}` matches any segment), narrowed by the service identity rules below; paths holding `${…}` are skipped, as are `${…}` binding and definition names. A bean's name is the `@Bean` `name`/`value` or the method name, or for a stereotype class its `value`, else the class name with a lower-case first letter.

Not covered: expanded Gateway `args` semantics, routes built with the Java DSL, Stream binding properties (`destination`, `group`, binder settings), service discovery, load balancer, circuit breaker and Spring Cloud Config settings.

## Hover and source actions

- **Hover**: a path variable bound once within one literal route, with explicitly imported known controller/mapping/PathVariable annotations; multiple routes, dynamic paths, foreign/shadow annotations and duplicate bindings stay quiet. GraphQL hover describes the current SDL field's named type and arguments, without inventing list/nullability/resolver semantics, and Java source hover documents exact imported `@QueryMapping` and `@SchemaMapping` annotations in `@Controller` classes (a literal field or the documented method-name default, Query's composed annotation contract, and an explicitly declared parent type; missing SchemaMapping type inference is UNRESOLVED). Messaging hover covers literal destinations of exact Spring JMS/Rabbit XML namespaces (not broker inference from Java receiver names) and literal `@KafkaListener(topics=…)`, `@RabbitListener(queues=…)` and `@JmsListener(destination=…)` declarations, including literal arrays; patterns/partitions/bindings, placeholders, concatenation, foreign annotations and unknown forms stay quiet. Container registration, inherited or composed metadata, installed versions, broker/subscription/delivery state and JMS queue/topic mode remain unresolved. These source-only providers perform no discovery, file reads, requests or processes.
- **Rename route variable and explicit binding…**: a lazy FileAction on a literal method route variable or its explicit `@PathVariable` name. It previews and returns two atomic source-token edits: `{id}` → `{newName}` and the annotation literal `"id"` → `"newName"`. The Java parameter identifier/body stay unchanged. Exact Spring imports, one method-level literal route, an explicit unique binding, no class-level route, ordinary closed Java source and a collision-free literal name are required. Kotlin, implicit parameter-name binding, inherited/class routes, regex/wildcard template variables, constants/concatenation and ambiguous aliases stay quiet. Selection/resolution use full current text/version/path/innermost owner and project-visible source checks around every prompt; cancellation returns no edits. Unsaved buffers, CRLF and UTF-16 are supported. No source write/process occurs. This changes this route's external variable spelling; it is not Java symbol Rename and does not update clients, other routes or runtime metadata.
- **OpenAPI source export**: **Tools → Copy Spring Endpoints as OpenAPI** copies a declaration-only OpenAPI 3.0.3 document from a complete fresh route index (optional clipboard permission). It includes explicit HTTP operations, literal path parameters, all matching handler identities, declared query/header parameters, literal `@ResponseStatus`/`ResponseEntity` codes, Bean Validation constraints and regex path-variable patterns where literal, consumes/produces media types and literal mapping conditions. ANY methods, wildcard paths, regex templates and ant-pattern mappings remain visible in `x-openidea-unexported-mappings`; conflicting handlers retain separate source metadata rather than guessed merged conditions; runtime conditions and request/response schemas are not inferred. No server is contacted. Positive source DTO shapes accompany the export: Java records, public fields, ordinary JavaBean getters, simple enum constants and public Kotlin data-class properties resolve through exact local package/import identities; arrays, supported collections/maps and recursive object references retain their written types; the export includes schema components and source provenance, only declared media types receive content entries, and media-unknown body/response shapes stay in source extensions. Custom serialization annotations, inheritance, generic DTO bindings, ambiguous names and Kotlin alias contexts remain unresolved; validation, requiredness and effective serializer naming/inclusion are not inferred. DTO schemas otherwise remain unspecified.
- **HTTP request lenses**: Java/Kotlin mapping methods offer a source-backed **HTTP request** code lens. Invocation checks the active source and version again; unrestricted mappings ask for an explicit HTTP method before generating a request or curl command. Named annotations imported from unrelated packages are not treated as Spring mappings. Generation uses source-qualified required query/header examples, literal positive mapping conditions and declared media types; query text is percent encoded; negative or contradictory conditions are shown for review or refused, and wildcard body media requires a concrete choice. Source/project/version are checked again after Base URL selection; existing request files are preserved. The source HTTP/GraphQL actions also work from Find Action: the active source supplies a native endpoint chooser when a lens payload is absent.
- **GraphQL request lenses**: root GraphQL query/mutation handlers offer schema-qualified HTTP request lenses. Generation requires a fresh complete local SDL/configuration model, preserves declared argument list/non-null types, checks shortcut annotation parents against the operation root and supports explicit `@SchemaMapping` custom roots, uses the configured servlet/GraphQL path, and refuses conflicting signatures or profile paths. The generated JSON POST uses editable argument samples and marks null custom-input values for review. Source/schema/configuration are checked again after origin selection. Subscription source lenses prepare a separate editable `.graphql` document from a proved SDL subscription root. Native source actions are shown only for positively matched complete local operation roots.
- **GraphQL subscriptions**: the optional **Start Reviewed GraphQL Subscription** command consumes one current `.graphql`/`.gql` subscription document, including documents prepared by source lenses. It requires Node 22 or newer with built-in WebSocket (optional `process:node`), then reviews the exact selected ws(s) endpoint, document, variables and connection initialization JSON before connecting; no application or Actuator credentials are reused. **Read GraphQL Subscription Output** polls bounded managed output, and **Cancel GraphQL Subscription** requests protocol Complete/close with a bounded process-kill fallback. Sessions last at most 120 seconds and end with plugin disposal. The helper uses `graphql-transport-ws`; it emits no unsupported native HTTP-file WebSocket syntax.

## Not implemented

- Sending requests from the plugin (the IDE's HTTP client owns execution).
- A versioned template inventory for the deferred unresolved-view check; GraphQL's broader non-root `unmapped-field` runtime-fetcher inference.
- Rename anchors and automatic rename behavior; framework resolution, composed annotations, schema/runtime wiring from libraries, full URI/type conversion, runtime routing/authorization.
- The source/cache subset here is narrower than full PSI/framework-based models.
